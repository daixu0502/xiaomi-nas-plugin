# 安装器 Shell 入口实测（2026-10-31）

本次针对实际 WSL 和 NAS 终端入口重新验收。最终候选为管理引擎 2.0.11、恢复组件 2.0.1、更新组件 2.0.0、公共权限组件 1.3.2，套件标识 `v2026.10.31.1`。这份记录补充此前 2.0.5 的验收，不将此前结果视为本次 Shell 入口的证明。

## 执行方式与数据范围

安装、重装、更新、卸载、修复及状态查询均由真实 PTY 中的 `sh manage.sh` 菜单执行；未通过直接调用 Python 安装函数代替用户入口。Windows 工作区源码是唯一来源，WSL 使用对应的 `/mnt/d/` 路径。检查脚本只承担断言、记录和明确限定的故障注入。

按用户授权在主账号测试，最终要求全新安装。先在 NAS 的 root 私有目录完整备份；普通卸载删除插件数据，保留数据重装和更新保留配置及启停意图。另一个空账号保持未安装。独立 SSH、Docker 容器及用户文件不属于本轮卸载范围。

## 发现并修复的问题

- 源码目录入口未自动找到已构建套件：现在读取 `dist/suite-artifacts.json` 并验证大小和摘要，也支持直接传入完整 `.tar.gz`。
- WSL 的 Windows 挂载目录不能作为可执行位依据：按签名清单重新设置传输和安装文件模式；新建共享父目录明确设置 0755，避免被安装器的 0077 umask 限制。
- 恢复和安装同时写入 `/etc/config/plugin` 与其 overlay 上层 backing 文件，真机复现 `ESTALE`。现在只写挂载路径；兼容旧事务记录并跳过无变化写入，恢复后重启清除旧失效句柄。挂载时直接修改底层目录不受支持，见 [Linux OverlayFS 文档](https://kernel.org/doc/html/v6.6/filesystems/overlayfs.html)。
- 最后一个插件卸载后仍有无引用公共代码和服务：现在提交后统一清理，保留固定锁 inode、明确卸载标记及未完成清理所需引导程序。
- 卸载依赖完好的插件脚本和恢复组件：现在按所属规范路径处理，停止 systemd 服务后以实际状态判断结果；从所属账号取得缓存目录描述符，释放缓存无需读取已丢失的 INFO 或控制脚本。
- 异常链接或不能唯一确定存储池阻断卸载：现在仅移除异常链接，列明保留外部目标；枚举账号在已挂载池中的规范位置。已知未挂载池持久登记延后清理，完成前阻止重新安装。
- NAS 复制目录时读取失效 INFO 链接的扩展属性导致备份失败：改为复制链接对象；残缺卸载的回退不会强制启动本就损坏的服务。该失败事务实际通过新入口 `recover` 完成恢复，再由菜单成功卸载。
- 保留数据重装不再清除 Mihomo 账号设置。错误提示保存失败阶段和回退材料路径，不输出大段内部执行代码。

只安装文件快传和下载中心时，公共权限组件代码与业务授权均为空。随后再次通过 NAS 菜单卸载，并由 WSL 菜单全新安装八插件。八插件原厂校验、目录权限、当前快照及业务接口通过；新任务与下载任务均为零。

实际重启后等待至少 125 秒，确认 boot ID 改变，再完成八插件原厂校验、业务接口、目录和快照复验。三个默认后台服务、任务调度及恢复监听正常，任务和运行记录均为零，没有未完成事务，空账号仍未安装。内核摘要、固定锁 inode 和独立 SSH 文件保持。

Openlist、Syncthing 原本运行，但 Docker 重启策略均为 `no`，本轮清空插件任务后不会自动启动。重启复验记录保留了这两项差异，随后显式恢复其运行状态，没有改变容器重启策略或补建任务；不能将此记为容器自动恢复通过。以后仍需通过原有独立方式启动这两个容器，或另行配置开机启动。

收尾再次确认全部 12 个容器与维护前的身份和启停状态一致，20 个已安装公共组件文件与最终签名套件一致。删除本轮 NAS 测试套件目录及哨兵文件，完整备份留在 NAS，大小 210,027,982 字节，SHA-256 为 `0affb186f2bd826ffefa918a1310e0ee97af6c7f796eac63a7457a2bb4dbdbd8`。重启前两次空闲状态采样的恢复监听 PID、checks 和 fullChecks 相同。

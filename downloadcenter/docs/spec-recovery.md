# 规范与恢复服务

安装完成会补齐 INFO、config、300×300 PNG、完整 resource 与 frontend，调用原厂校验并登记独立恢复服务。详见集中分发目录的恢复说明。

`etc/var` 使用指向 `/data/minas/plugins/data/<用户>/<插件>/` 的受控链接；普通缓存仍使用官方 tmp。手动 `manage.sh uninstall` 取消自动恢复登记，持久数据保留。应用市场的删除会由恢复服务补回；确实要删除请使用 manage.sh。

固件清除 systemd 与 Cron 后，需在 root 终端执行：

```sh
python3 -B /data/minas/plugins/recovery/recovery.py bootstrap
```

恢复服务 1.1.1 会初始化官方 plugintmp 上级目录的用户组权限，再降权创建和检查插件缓存；不递归操作其他插件缓存。即使 tmp 链接仍存在但目标被删除，也会重建目标。

启用状态优先采纳原厂日志中明确且成功的启用/停用命令（原厂命令不更新 changetime），并支持带更新 changetime、未下架且完整的注册信息；系统启动、下架卸载中的钩子调用不会覆盖保存意图。原厂完整卸载会停止后台服务；恢复后按保存的启用及运行状态恢复，任务中心只恢复调度器状态，不手动重放任务，SSH 恢复动作也不会自动执行。

恢复服务 1.2.0 将 Mihomo、快传和下载中心交给独立 systemd 服务托管，仍以所属 NAS 用户运行，避免 recovery oneshot 退出时清理后台进程。页面通过固定范围的服务入口启停；主动停止意图独立保存，生命周期卸载停止不覆盖意图。明确 manage.sh 卸载会移除服务和授权。

恢复服务 1.3.0 使用 inotify 监听注册表、源码和入口目录的变化，等待原厂操作结束并合并事件后恢复；不监听 etc/var/tmp 内容。开机和存储池挂载后补查。健康空闲时阻塞等待内核事件，不执行定时源码摘要扫描；注册状态事件只核对状态，源码异常或实际恢复才完整校验。运行暂存和监听状态位于 /run/minas-plugin-recovery/，持久启停意图仍保存在受保护目录。

旧 30 秒定时器已移除；每分钟 Cron 只通过 systemctl 检查监听服务是否存活，正常时不启动 Python。监听服务或单元丢失时才尝试启动或 bootstrap。目录重建和事件队列溢出会重新监听并补查；普通容器挂载变化不触发存储池扫描。失败最多重试两次，随后等待新事件或手动 reconcile，避免持续扫描冲突源码。
